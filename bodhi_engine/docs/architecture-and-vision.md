# Bodhi — Architecture & Vision

## How It Works Today

Bodhi DSL is generated by AI as a byproduct of writing code. The AI (Claude Code, Cursor, etc.) writes code and
simultaneously produces `@bodhi.*` inline tags and `.bodhi/` YAML files. The system is split into two layers:

```
Developer describes requirements
     ↓
AI writes code + generates DSL
     ↓
bodhi validate (CLI / CI)
```

### Two-Layer Architecture

```
┌─────────────────────────────────────────────────────────────────────┐
│  bodhi_app — Application Layer                                      │
│                                                                     │
│  CLI (bodhi_app/cli/)              MCP Server (bodhi_app/mcp/)      │
│  ├── main.py        entry point    ├── server.py       single svc   │
│  ├── show.py        terminal viz   └── workspace_server.py  multi   │
│  └── graph.py       mermaid/html                                    │
│                                    Diagnosis (bodhi_app/diagnose.py) │
├─────────────────────────────────────────────────────────────────────┤
│  bodhi_engine — Core Engine                                         │
│                                                                     │
│  Parser (bodhi_engine/parser/)     Knowledge Graph                  │
│  ├── inline.py      @bodhi.* tags  └── knowledge.py                 │
│  └── yaml_parser.py .bodhi/ YAML      ├── query_flow                │
│                                       ├── trace_entity              │
│  Validator                            ├── impact_analysis           │
│  └── checker.py     rules engine      ├── match_log                 │
│                                       └── ...                       │
│  Deriver                                                            │
│  └── deriver.py     scaffold L2    Workspace                        │
│                                    └── workspace.py  multi-service  │
├─────────────────────────────────────────────────────────────────────┤
│  Project Source                                                     │
│  ├── Source code with @bodhi.* inline tags                          │
│  └── .bodhi/ YAML (flows, entities, events, states, services, ...) │
└─────────────────────────────────────────────────────────────────────┘
```

**bodhi_engine** is the core library — it parses DSL, builds an in-memory knowledge graph, validates consistency,
and provides query methods. It has no UI, no I/O beyond file reading, and no framework dependencies beyond PyYAML.

**bodhi_app** is the application layer — it consumes bodhi_engine and exposes it to users and AI agents:

- **CLI** (`bodhi_app/cli/`) — all `bodhi` commands: `validate`, `check`, `stats`, `derive`, `show flow`,
  `show stats`, `graph`, `serve`, `serve-all`, `workspace-validate`
- **Terminal visualization** (`show.py`) — colored flow call chains and coverage dashboards using `rich`
- **Graph export** (`graph.py`) — Mermaid diagrams with HTML/SVG/PNG output, DB nodes grouped by datasource
- **MCP Server** (`bodhi_app/mcp/`) — exposes the knowledge graph to AI coding assistants via MCP protocol
- **Log diagnosis** (`diagnose.py`) — matches log snippets against `@bodhi.log.*` patterns

### MCP Server

Bodhi runs as a local MCP (Model Context Protocol) server that AI coding assistants can query in real time.

```json
{
  "mcpServers": {
    "bodhi": {
      "command": "bodhi",
      "args": [
        "serve",
        "/path/to/your-project"
      ]
    }
  }
}
```

On startup, the engine scans the project, parses all inline tags and `.bodhi/` YAML files, and builds an in-memory
knowledge graph. It then exposes MCP tools that AI agents can call to query the graph.

For multi-service workspaces, `bodhi serve-all` starts a federated MCP server that merges knowledge graphs from
multiple service repos and validates cross-service consistency.

### What AI Agents Can Do With It

| Tool              | What It Does                                      | Example Query                                  |
|-------------------|---------------------------------------------------|------------------------------------------------|
| `query_flow`      | Return a complete request-to-response call chain  | "How does the create order API work?"          |
| `trace_entity`    | Find all functions that read/write a given entity | "What touches the `orders` table?"             |
| `find_consumers`  | Find all consumers of a given event               | "What happens when `order_created` fires?"     |
| `impact_analysis` | Trace the blast radius of a change                | "What breaks if I change the `status` field?"  |
| `query_state`     | Return state machine transitions                  | "What are the valid transitions from PAID?"    |
| `service_deps`    | Return upstream/downstream service dependencies   | "What does order-service depend on?"           |
| `query_channel`   | Return a bidirectional channel definition         | "What events does the order WebSocket handle?" |
| `query_topology`  | Return a cross-service event chain                | "How does the order fulfillment flow work?"    |
| `diagnose_log`    | Match log snippets against pattern registry       | "What function produced this error log?"       |

The key insight: DSL tells the AI **where to look and what to ask**, turning open-ended questions into targeted queries.

giving AI agents a unified way to query both structure and runtime data.

### Example: AI-Powered Debug Session

With all data sources connected, an AI agent can autonomously debug a production issue:

```
Ops asks: "Why didn't order ORD-99 complete?"

1. Query DSL → order_lifecycle state machine
   → PAID → COMPLETED requires event(delivery_confirmed)

2. Query DB → SELECT status FROM orders WHERE id = 'ORD-99'
   → status = 2 (FAILED), never reached PAID

3. Query DSL → create_order flow, locate PaymentService.charge step
   → on_fail: payment_timeout → retry 3 → reject 500
   → log.error: "Payment failed for order {orderId}: {reason}"

4. Query Logs → search "Payment failed for order ORD-99"
   → "Payment failed for order ORD-99: insufficient_balance"

5. Answer: "Order ORD-99 failed during payment due to insufficient
   balance. Status is FAILED(2), never reached PAID. Failure occurred
   at PaymentService.charge, retried 3 times then returned 500."
```

Without DSL, the AI would have to scan the entire codebase to understand the order flow, guess which tables to query,
and grep logs blindly. DSL gives it a structured map to follow.

## Long-Term Vision

### Cross-Repo / Cross-Service

Each microservice repo has its own `.bodhi/` directory. Bodhi Engine can aggregate DSL from multiple repos to build
a global service dependency graph:

- "What breaks if payment-service goes down?" — trace `depends_on` across all services
- "What ultimately happens when `order_created` fires?" — follow `emits` → `consumes` chains across repos
- Full request path from API gateway to database, statically — no Jaeger needed for understanding the architecture

### Intent-to-Code Generation

Write `.bodhi/` YAML first (flows, entities, events, states), then let AI generate the code from the DSL. The DSL
becomes a high-level "intent programming" language:

```
Write flows + entities + events → AI generates code + inline tags
```

### Automated Architecture Compliance

Define rules and enforce them in CI:

- All write operations must have `on_fail`
- All remote calls must have `circuit_breaker` or `retry`
- All PII fields must be marked `sensitive: true`
- All events must have at least one consumer

### Living Architecture Diagrams

Auto-generate from DSL data — always in sync with code because the data source *is* the code.

Already implemented:

- Flow call graphs from `flows/` (`bodhi graph`, Mermaid/HTML output, DB nodes grouped by datasource)
- Terminal flow visualization (`bodhi show flow`, colored call chain)
- Coverage dashboards (`bodhi show stats`, per-tag progress bars)

Future:

- C4 models from `services/` + `flows/`
- Sequence diagrams from `flows/` steps
- ER diagrams from `entities/` + relations
- State machine diagrams from `states/`

### AI Onboarding Agent

New developer asks questions, AI answers from the knowledge graph:

- "How does the order flow work?" → walks through the flow step by step
- "What does this field mean?" → reads entity + concepts
- "What does this service depend on?" → reads services + resilience config
- "What happens if this fails?" → reads on_fail chains + circuit breakers

An always-on, always-accurate system explainer.
